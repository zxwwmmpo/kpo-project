# Порядок управления исходным кодом

## Оформление коммитов

Используется соглашение Conventional Commits.

Формат сообщения:

type(scope): краткое описание

Область scope необязательна.

Типы коммитов:
- feat — новая функциональность;
- fix — исправление ошибки;
- docs — изменение документации;
- style — форматирование без изменения поведения;
- refactor — изменение структуры кода без изменения поведения;
- test — добавление или изменение тестов;
- build — изменения сборки и зависимостей;
- ci — настройка автоматических проверок;
- chore — прочие технические задачи.

Примеры:
- feat(auth): add user registration
- fix(profile): correct contact validation
- docs: update setup instructions
- ci: add commit message validation

Один коммит должен содержать одно логически завершённое изменение.
Описание должно кратко объяснять внесённое изменение.
Пароли, токены, локальные настройки и результаты сборки не добавляются
в репозиторий.

## Ветвление

Используется стратегия GitHub Flow.

Основная ветка — main.
Для каждой задачи создаётся отдельная ветка от актуальной main.

Примеры названий:
- feat/auth
- fix/profile-validation
- docs/setup-guide
- chore/repository-workflow

После слияния рабочая ветка удаляется.

## Слияние

Изменения в main вносятся через Pull Request.

Порядок:
1. Создать рабочую ветку от актуальной main.
2. Внести изменения и создать коммиты.
3. Отправить ветку на GitHub.
4. Создать Pull Request с описанием изменений.
5. Дождаться успешного завершения обязательных проверок.
6. Просмотреть изменения и устранить замечания.
7. Выполнить Squash and merge.
8. Удалить рабочую ветку.

Заголовок Pull Request и сообщение итогового squash-коммита
должны соответствовать Conventional Commits.

Прямые изменения main после настройки защиты запрещены.

## Контроль качества

Планируемые обязательные проверки:
- commitlint — сообщения коммитов и заголовок Pull Request;
- Checkstyle — проверка Java-кода;
- Spotless — проверка форматирования Java-кода;
- ESLint — проверка TypeScript и React;
- Prettier — проверка форматирования фронтенда;
- сборка и автоматические тесты проекта.

Проверки выполняются в GitHub Actions.
Неуспешные обязательные проверки блокируют слияние.

## Релизы

Релиз создаётся из main после успешного прохождения проверок.

Версии обозначаются тегами вида vMAJOR.MINOR.PATCH:
- MAJOR — несовместимые изменения;
- MINOR — новая обратно совместимая функциональность;
- PATCH — обратно совместимые исправления.

Для начальной разработки используются версии 0.x.y.
Первый демонстрационный релиз — v0.1.0.

Для тега создаётся GitHub Release с описанием изменений
и состоянием реализованной функциональности.
